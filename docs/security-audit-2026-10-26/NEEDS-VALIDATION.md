## VPS Caddyfile always serves the unauthenticated bundled ntfy on public 443 under the placeholder name ntfy.localhost, contradicting its own 'never reachable' promise

`server/Caddyfile:ntfy-placeholder-site:sni-reachable`

The VPS overlay promises that leaving CM_NTFY_DOMAIN unset keeps the bundled ntfy private (server/Caddyfile:13-15, docs/DEPLOY-VPS.md:142-143). Source shows the opposite configuration: docker-compose.vps.yml:44 passes CM_NTFY_DOMAIN=ntfy.localhost to the Caddy container whenever the variable is unset or empty (compose `:-` default; server/.env.example:67 ships it empty, and docs/DEPLOY-VPS.md:33 tells the operator to copy that file), and server/Caddyfile:16-17 unconditionally declares a second HTTPS site for that name that reverse-proxies to ntfy:80. The Caddyfile has no global options (no auto_https off, no strict_sni_host, no listener restriction), so both sites share the single :443 listener that docker-compose.vps.yml:38-41 publishes on every interface of the public VPS. Caddy routes HTTP requests by the client-supplied Host header and, for *.localhost names, issues an internal certificate instead of refusing the site; if that is confirmed at caddy 2.11.7, any internet client that connects to the VPS's 443 with SNI/Host `ntfy.localhost` (curl -k --resolve), or completes TLS under the real CM_DOMAIN certificate and sends `Host: ntfy.localhost`, reaches the ntfy container. The ntfy service (server/docker-compose.yml:74-78) runs `serve` with no auth-file or auth-default-access setting, i.e. ntfy's default anonymous read-write on every topic. Concrete result if validated: anyone on the internet can publish to and subscribe on any topic of the owner's ntfy. Because server/.env.example:29 sets CM_NTFY_URL=http://ntfy (the bundled instance; docs/DEPLOY-VPS.md:143 wrongly says ntfy.sh is used in that case), a default VPS install publishes real alerts there: a subscriber who knows or guesses an operator-chosen contact topic (4-64 chars of letters, digits, - and _, wearers.py:258-259) reads the wearer's name, detector and Google-Maps location (channels.py:23-36) and the raw acknowledge URL carried in the `Actions` header (channels.py:83-84, main.py:485), which lets them POST /api/v1/ack/{token} (main.py:339-341) and record an acknowledgement for that contact; they can also push spoofed 'Standby' notifications to a contact's topic. In every configuration the owner's IP hosts an open anonymous push relay. The configuration is a maintained deployment path (docs/DEPLOY-VPS.md) but not the owner's NAS production, so live exposure depends on whether the overlay is deployed and on provider behaviour that must be rendered or observed.

**Claimed root cause:** server/Caddyfile:16 uses the Caddyfile default `{$CM_NTFY_DOMAIN:ntfy.localhost}` (and docker-compose.vps.yml:44 the compose default `${CM_NTFY_DOMAIN:-ntfy.localhost}`) as if an unset variable disabled the ntfy site. Caddy has no conditional site emission: a `*.localhost` site address is a fully served site on the shared public :443 listener, selected by client-supplied SNI/Host rather than by DNS, and certified by Caddy's internal issuer, so the 'placeholder' remains routable from any peer that reaches port 443.

### Source trace
1. **entrypoint** `server/docker-compose.vps.yml:40` (services.caddy.ports): Caddy's 443 (plus 80 and 443/udp, lines 39-41) is published without a host_ip, i.e. on all interfaces of the public VPS; any internet client reaches this listener.
2. **propagation** `server/docker-compose.vps.yml:44` (services.caddy.environment.CM_NTFY_DOMAIN): `${CM_NTFY_DOMAIN:-ntfy.localhost}` hands the Caddy container the literal ntfy.localhost whenever the operator leaves the variable unset or empty (as server/.env.example:67 ships it).
3. **propagation** `server/Caddyfile:16` (site block {$CM_NTFY_DOMAIN:ntfy.localhost}): A second HTTPS site for host ntfy.localhost is always declared on the same default :443 server as {$CM_DOMAIN}; no global options restrict listeners, SNI or automatic HTTPS, so Caddy matches it on the client-supplied Host (and obtains an internal certificate for the .localhost name) — provider behaviour to be rendered.
4. **propagation** `server/Caddyfile:17` (reverse_proxy ntfy:80): Matching requests are forwarded unchanged to the ntfy container over the compose network.
5. **sink** `server/docker-compose.yml:75` (services.ntfy.command serve): ntfy v2.28.0 runs `serve` with no NTFY_AUTH_FILE / NTFY_AUTH_DEFAULT_ACCESS and no tracked server.yml, i.e. the provider default of anonymous read-write on every topic: subscribe (read alert bodies and raw ack URLs), publish (spoof alerts), relay.

### Verified evidence
- `server/Caddyfile:13`: Comment (lines 13-15) asserts 'Leave CM_NTFY_DOMAIN unset to keep it private (the placeholder host is never reachable from outside)'; the site block below contradicts this because Caddy site selection depends on the client's SNI/Host, not on DNS.
- `server/Caddyfile:16`: `{$CM_NTFY_DOMAIN:ntfy.localhost} {` with `reverse_proxy ntfy:80` on line 17 emits the ntfy site unconditionally; the file has no global options block (no auto_https off, strict_sni_host or bind directive).
- `server/docker-compose.vps.yml:29`: NTFY_BASE_URL defaults to https://ntfy.localhost and NTFY_BEHIND_PROXY=true (line 30): the overlay itself treats the placeholder name as the served base URL of the ntfy site.
- `server/docker-compose.vps.yml:38`: services.caddy.ports publishes 80, 443 and 443/udp on all interfaces (lines 39-41); the ntfy container's own port is pinned to 127.0.0.1:8090 (line 27), so Caddy is the only but sufficient path.
- `server/docker-compose.yml:74`: ntfy image v2.28.0 with `command: serve` (line 75) and no auth-related environment or config volume other than the data dir; no ntfy server.yml is tracked in the repository.
- `server/.env.example:29`: CM_NTFY_URL=http://ntfy: the file the VPS guide tells operators to copy publishes alerts to the bundled ntfy, so the reachable instance carries real alerts (docs/DEPLOY-VPS.md:143's claim that ntfy.sh is used without CM_NTFY_DOMAIN does not match this default).
- `server/.env.example:67`: CM_NTFY_DOMAIN= ships empty; compose's `:-` default therefore substitutes ntfy.localhost for both the Caddy site and NTFY_BASE_URL.
- `docs/DEPLOY-VPS.md:33`: `cp .env.example .env` is the prescribed setup step, so the defaults above are the default VPS deployment.
- `docs/DEPLOY-VPS.md:142`: Operator-facing doc repeats that without CM_NTFY_DOMAIN 'the bundled ntfy stays private to the VPS' (lines 142-143).
- `server/app/channels.py:83`: Every ntfy alert carries `Actions: http, Acknowledge, {ack_url}, method=POST, clear=true` (lines 83-84), and the body (lines 23-36) holds the wearer's name, detector and a Google-Maps location link; a topic subscriber obtains the raw ack URL.
- `server/app/main.py:485`: ack_url is built from PUBLIC_URL and the raw ack token; POST /api/v1/ack/{ack_token} (lines 339-341) records the acknowledgement for the contact with possession of the token as the only check (do_ack, lines 306-319).
- `server/app/wearers.py:258`: Contact ntfy topics are operator-chosen strings of 4-64 letters, digits, - and _ (lines 258-259); nothing enforces unguessable topics.

### Exact blockers
- Caddy 2.11.7 behaviour is a provider fact outside the repository and could not be rendered in this run (no execution permitted): that both site blocks land on one :443 server routed by Host, that a *.localhost address is served with an internal-issuer certificate rather than refused, and that strict_sni_host is off by default so a Host: ntfy.localhost request under the CM_DOMAIN certificate also reaches the ntfy route.
- ntfy v2.28.0's default of anonymous read-write access with no auth-file / auth-default-access configured is a provider default outside the repository; it decides whether reachability means open read/publish or only an unauthenticated health endpoint.
- Whether the VPS overlay (docker-compose.vps.yml + Caddyfile) is deployed anywhere today is not source-visible (docs/SECURITY-AUDIT-2026-10-13.md:194-196 asked the same question); the owner's NAS production uses the base compose without Caddy, where this path does not exist.
- Whether a deployed VPS .env sets CM_NTFY_DOMAIN (intentionally public ntfy) or leaves it unset (the failing privacy claim), and whether CM_NTFY_URL points at the bundled instance (alerts readable) or ntfy.sh (open relay only), cannot be read in this audit.

### Resolution plans
- **Local (bounded fixture):** On any machine with the caddy 2.11.7 binary, no network needed and nothing deployed: `CM_DOMAIN=standby.example.org CM_NTFY_DOMAIN=ntfy.localhost caddy adapt --config server/Caddyfile --adapter caddyfile --pretty`. Expected if the candidate holds: one server under apps.http.servers listening on [":443"] whose routes include a route with `match: [{"host": ["ntfy.localhost"]}]` and a reverse_proxy handler with upstream dial `ntfy:80`, no `strict_sni_host` key, and an apps.tls.automation policy whose subjects include ntfy.localhost with `issuers: [{"module": "internal"}]`. Then `caddy validate --config server/Caddyfile --adapter caddyfile` with the same env must succeed. A rendering that puts the ntfy site on a different listener, omits it, or rejects the name refutes the candidate. Optionally, in an offline container, `caddy run` with that Caddyfile plus a stub listener on ntfy:80 and `curl -sk --resolve ntfy.localhost:443:127.0.0.1 https://ntfy.localhost/` must return the stub's response.
- **Owner-observed deployment check:** Owner only, on the VPS host over loopback, nothing sent from elsewhere and nothing changed: (1) `docker compose ps` to record whether the caddy service from docker-compose.vps.yml is running at all; (2) `grep -E '^(CM_NTFY_DOMAIN|CM_NTFY_URL)=' .env` to record intent (do not share the file); (3) `curl -sk --resolve ntfy.localhost:443:127.0.0.1 https://ntfy.localhost/v1/health` — a JSON `{"healthy":true}` reply proves ntfy is served through Caddy's public 443 under the placeholder name, a TLS alert or Caddy 404/empty reply refutes it; (4) `curl -s --resolve <CM_DOMAIN>:443:127.0.0.1 -H 'Host: ntfy.localhost' https://<CM_DOMAIN>/v1/health` — the same JSON shows the route is reachable without any certificate warning; (5) anonymous access: `curl -sk --resolve ntfy.localhost:443:127.0.0.1 -d probe https://ntfy.localhost/standby-audit-probe-<random>` followed by `curl -sk --resolve ntfy.localhost:443:127.0.0.1 'https://ntfy.localhost/standby-audit-probe-<random>/json?poll=1'` on a throwaway topic; a 200 publish and the message echoed back prove default read-write for anonymous clients (HTTP 403 refutes the impact branch).

## A single wearer token can fill the shared ./data volume with diagnostics bundles; a full volume would block SQLite writes that every escalation send depends on

`server/app/diagnostics.py:upload:no-per-wearer-quota`

POST /api/v1/diagnostics (server/app/diagnostics.py:74-116) is reachable with any valid wearer bearer token (require_wearer, wearers.py:71-77) and stores every accepted body as <CM_DATA_DIR>/diagnostics/<wearer>/<server-generated id>.zip plus one row in the diagnostics table. The only bounds are per request: a Content-Length pre-check (line 82) and a streamed cap of MAX_BYTES, 20 MiB by default (line 97). There is no per-wearer count, aggregate-byte or rate limit anywhere on the path: add_diagnostics (store.py:495-500) inserts unconditionally, the bundle id is a fresh time+random string per call (line 85), an admin 'request' is optional (request_id is None is accepted, line 111), and the only cleanup is age-based (purge_expired, lines 55-63, RETENTION_DAYS=30, run at most hourly, lines 66-71). The upstream layers add no cap: the Caddyfile has no request_body limit (Caddyfile:10), uvicorn is started without body limits (Dockerfile:34), and docker-compose.yml passes neither CM_DIAG_MAX_BYTES nor CM_DIAG_RETENTION_DAYS into the container (environment block lines 20-56; .env.example:59-60 documents them anyway), so the shipped deployment runs on the defaults. Attacker cost is low: a wearer token (an enrolled wearer, or anyone who copied the token from a phone) and upload bandwidth; a 4-byte body b'PK\x03\x04' passes the magic check (line 102) if the goal is row and inode growth rather than bytes, and 20 MiB bodies grow the volume at line rate. Persistence is 30 days per bundle. Shared blast radius: bundles, cryomonitor.db (store.py:104), ./data/ntfy (compose line 80) and, in the VPS overlay, Caddy's certificate and config state (docker-compose.vps.yml:47-48) all live on the one writable bind mount ./data:/srv/data (compose line 68); mem_limit (line 17) bounds memory only and no storage quota is declared. The project's own VPS guide sizes the machine at 10 GB disk (docs/DEPLOY-VPS.md:5), i.e. on the order of 500 maximum-size uploads. Safety-function impact if the volume fills: the pump inserts an ack token into SQLite before any send (main.py:394, design D3) and create_escalation persists before returning (main.py:141), so a failing write turns a wearer's alarm POST into a 500 and raises out of pump_cycle, where _pump_loop logs and retries the whole cycle (main.py:525-530) — no escalation of any wearer on the instance is delivered until space is freed; heartbeats also write (main.py:200-203) and would fail too. Recovery is poor: no disk-usage alert exists in the stack, and the dashboard deletes one bundle per CSRF-protected POST (ui.py:441-448), so an operator would have to clean up from a shell. What source cannot settle: whether the host enforces a quota on ./data (and how much free space the volume has), and the exact behaviour of SQLite in WAL mode (store.py:129) plus the pump on ENOSPC (a WAL file with already-allocated space can absorb some commits before SQLITE_FULL surfaces). The missing-bound half of the claim is established from source only in this run; no target code was executed.

**Claimed root cause:** diagnostics.upload enforces only a per-request size cap and never consults the wearer's existing bundle count, aggregate bytes or upload rate, while the bundle store shares the single writable volume that the safety-critical SQLite writes (ack tokens, escalation state, heartbeats) depend on.

### Source trace
1. **entrypoint** `server/app/diagnostics.py:74` (upload): POST /api/v1/diagnostics; the only authentication is require_wearer(authorization) at line 77, so any holder of a valid wearer bearer token reaches it, with or without an admin diagnostics request.
2. **propagation** `server/app/diagnostics.py:82` (upload): Per-request bounds only: Content-Length pre-check here and the streamed 'if size > MAX_BYTES' (20 MiB default, line 23) at line 97. No COUNT or SUM over the wearer's existing bundles, no rate limit, no upstream body limit (Caddyfile:10, Dockerfile:34).
3. **propagation** `server/app/diagnostics.py:104` (upload): os.replace makes the bundle permanent under <CM_DATA_DIR>/diagnostics/<wid>/<diag_id>.zip; diag_id is a fresh server-generated id per call (line 85), and a 4-byte body b'PK\x03\x04' satisfies the magic check at line 102, so rows and inodes can accumulate at minimal per-request cost.
4. **propagation** `server/app/store.py:498` (Store.add_diagnostics): Unconditional INSERT into diagnostics (called from diagnostics.py:110); the table is only pruned by age via diagnostics_older_than (lines 519-523) from purge_expired (30 days).
5. **propagation** `server/docker-compose.yml:68` (services.monitor.volumes): ./data:/srv/data is the single writable mount (container is read_only with tmpfs /tmp, lines 11-13) holding diagnostics/, cryomonitor.db (store.py:104) and ./data/ntfy (line 80); no storage quota is declared, and the VPS overlay adds Caddy's cert/config state to the same tree (docker-compose.vps.yml:47-48).
6. **sink** `server/app/main.py:394` (_ack_token_for): db.add_ack_token must succeed before any send (design D3). On a full volume the INSERT raises out of pump_cycle; _pump_loop (lines 525-530) logs and retries the whole cycle every 5 s, so no escalation of any wearer is delivered until space is freed.

### Verified evidence
- `server/app/diagnostics.py:97`: The only size control on the path: 'if size > MAX_BYTES' per request (MAX_BYTES from CM_DIAG_MAX_BYTES, default 20 MiB, line 23).
- `server/app/diagnostics.py:110`: db.add_diagnostics(wid, diag_id, size, days, request_id) is called with no check of the wearer's existing bundle count or bytes; request_id may be None (line 111), so no admin request is needed.
- `server/app/diagnostics.py:59`: purge_expired deletes only rows with created_t older than RETENTION_DAYS (30) days; purge_if_due runs it at most hourly (lines 66-71). Nothing else frees space automatically.
- `server/app/store.py:104`: The SQLite file cryomonitor.db lives in the same CM_DATA_DIR as the bundles; connections use WAL mode (line 129).
- `server/app/main.py:141`: create_escalation calls _persist_escalation (db.save_escalation) before returning, so a failing write turns POST /api/v1/alarm (line 248-261) into a 500.
- `server/app/main.py:527`: _pump_loop catches any exception from pump_cycle, logs it and retries after 5 s; a persistent write failure means no cycle completes and no sends happen for any wearer.
- `server/app/ui.py:441`: Deletion is one bundle per CSRF-protected admin POST; no bulk or per-wearer purge exists in the UI or the API.
- `server/docker-compose.yml:20`: The environment block passes neither CM_DIAG_MAX_BYTES nor CM_DIAG_RETENTION_DAYS and there is no env_file, so the knobs documented at server/.env.example:59-60 are inert in the shipped deployment.
- `server/Caddyfile:10`: reverse_proxy monitor:8080 with no request_body max_size, so the VPS proxy adds no upload cap.
- `docs/DEPLOY-VPS.md:5`: The recommended VPS tier has a 10 GB disk, i.e. roughly 500 maximum-size bundles would fill the volume that also holds cryomonitor.db and Caddy's certificates.

### Exact blockers
- Whether the host filesystem under ./data enforces a quota for UID 10001 or the shared folder (Synology shared-folder quota; VPS partition layout and free space) is a deployment fact not visible in source. Without a quota the shared-impact chain holds; with one the blast radius shrinks to the diagnostics directory.
- The behaviour of SQLite in WAL mode and of the pump when the volume is full (when SQLITE_FULL surfaces on the ack-token INSERT and the escalation UPSERT, given that an already-allocated WAL file can absorb some commits) is a runtime fact that this run's policy forbids demonstrating; the pytest tmp_path fixture cannot produce a size-bounded filesystem, so a throwaway size-limited mount is needed.

### Resolution plans
- **Local (bounded fixture):** Step 1 (missing bound, existing fixtures, no filesystem tricks): in server/tests, with the appenv fixture from conftest.py, loop 50 times posting content=b'PK\x03\x04' to '/api/v1/diagnostics?days=1' with headers {'Content-Type': 'application/zip', **wearer_headers()} (the _upload helper in tests/test_diagnostics.py already does this); assert every response is 200, that appenv.store.list_diagnostics('default') has 50 rows, that os.listdir(os.path.join(os.environ['CM_DATA_DIR'], 'diagnostics', 'default')) has 50 files, and that app.diagnostics.purge_expired(time.time()) returns 0 and leaves all 50. Step 2 (shared-volume effect, optional, Linux throwaway environment only, never the live service): mount a small tmpfs (e.g. mount -t tmpfs -o size=16m tmpfs /mnt/cmtest) and run the same fixture with CM_DATA_DIR pointing at it (monkeypatch before _build_appenv), enrol a second wearer via the admin API, upload 20 MiB-capped bundles with the first wearer's token until a 500 or 413 appears, then POST /api/v1/alarm with the second wearer's token and call await appenv.main.pump_cycle(); record whether the alarm POST returns 500 and whether pump_cycle raises sqlite3.OperationalError ('database or disk is full') from add_ack_token with appenv.fakes['telegram'].sent still empty. Record the free space in units of 20 MiB and whether any disk-usage alert or quota exists for that volume. If no quota separates diagnostics from cryomonitor.db, the shared-impact chain stands; if a quota exists, note its size.

## A wearer heartbeat with suspended_until = +Infinity makes every operator fleet and wearer page fail with HTTP 500 until a finite or null value is stored

`server/app/main.py:heartbeat:suspended_until-unbounded-float-dashboard-overflow`

POST /api/v1/heartbeat (wearer bearer token) accepts `suspended_until` as a plain `float | None` (server/app/main.py:160) and stores it verbatim in deadman.suspended_until REAL (main.py:204, store.py:480-485). FastAPI hands an application/json body to starlette Request.json(), which is stdlib json.loads; that parser turns the non-standard literal `Infinity` and the grammar-valid number `1e999` into float('inf'), and pydantic's float field accepts inf by default (allow_inf_nan True). ui.wearer_states (server/app/ui.py:91-94) then evaluates `susp > time.time()` (True for +inf) and `int((susp - time.time()) / 60)`, which raises OverflowError. wearer_states is called for every enabled wearer by build_fleet (ui.py:106, used by GET /ui/ at 179 and GET /ui/fragments/fleet at 187) and for the affected wearer by _render_wearer (198, GET /ui/wearers/{wid}) and wearer_fragment (247). Starlette's ServerErrorMiddleware turns the exception into a 500, so one request from one wearer token (an enrolled phone or a stolen token on a shared instance) makes the fleet view unavailable to every operator, across all tenants, while the value stays stored. The pump loop, alarm delivery, ack links, /api/v1/status, /ui/operators and /ui/audit do not read the value and keep working. The value is overwritten by the wearer's next heartbeat: the real companion omits the key when not paused (android ServerClient.kt:173), so a legitimate phone that still heartbeats every 5 minutes clears it, which makes persistence depend on the attacker re-sending (cheap) or on the attacker holding the only copy of that wearer's token. Operator recovery without a sane heartbeat is manual: an admin can obtain a CSRF token from a still-rendering page such as /ui/operators and POST /ui/wearers/{wid}/disable (ui.py:451, redirects without rendering), or call POST /api/v1/admin/wearers/{wid}/disable with the admin session cookie (wearers.py:200); disabled wearers return before the suspended check (ui.py:57). Only +Infinity triggers the failure: NaN and -Infinity fail the `susp > time.time()` comparison and huge finite values produce a large but valid integer label. Corrections to the hunter's record: the sink is ui.py:94 (the comparison is at 92), not 88/91.

**Claimed root cause:** HeartbeatIn.suspended_until (server/app/main.py:160) has no range or finiteness validation and is persisted verbatim, and ui.wearer_states (server/app/ui.py:92-94) converts the stored float to int without guarding non-finite values; the stdlib JSON decoder used by Starlette and pydantic's default allow_inf_nan=True let +inf reach the model.

### Source trace
1. **entrypoint** `server/app/main.py:190` (heartbeat): Wearer-token route `POST /api/v1/heartbeat`; the body is validated as HeartbeatIn whose `suspended_until: float | None = None` (line 160) carries no ge/le constraint and no finiteness check.
2. **propagation** `server/.venv/Lib/site-packages/fastapi/routing.py:446` (get_request_handler.app): For content-type application/json FastAPI calls `await request.json()` (line 439 when no content-type is sent); starlette Request.json (requests.py:265, installed 1.3.1) is `json.loads(body)`, whose default parse_constant maps the `Infinity` literal to float('inf') and whose number grammar turns `1e999` into inf. The resulting Python dict is validated in python mode, where pydantic_core's float schema allows inf by default.
3. **propagation** `server/app/main.py:204` (heartbeat): `db.set_suspended_until(auth.wearer_id, hb.suspended_until)` is executed unconditionally on every heartbeat with the raw value.
4. **propagation** `server/app/store.py:482` (Store.set_suspended_until): Upsert into `deadman.suspended_until` (column added as REAL at store.py:110/117); get_suspended_until (487-491) returns the stored value unchanged.
5. **propagation** `server/app/ui.py:92` (wearer_states): `susp = db.get_suspended_until(wid)` (91) then `if susp and susp > time.time():` — True for +inf, False for NaN and -inf.
6. **sink** `server/app/ui.py:94` (wearer_states): `f"suspended {int((susp - time.time()) / 60)}m"` — int() of an infinite float raises OverflowError; the exception propagates out of build_fleet (106) into fleet_page (179) and fleet_fragment (187), and out of _render_wearer (198) and wearer_fragment (247), becoming an HTTP 500 via Starlette's ServerErrorMiddleware.

### Verified evidence
- `server/app/main.py:160`: `suspended_until: float | None = None` on HeartbeatIn — no bounds, no finiteness validator; `Field` is not even imported in main.py (lines 18-20).
- `server/app/ui.py:57`: `if not w["enabled"]: return 0, [...]` — a disabled wearer returns before the suspended check, so disabling is the operator-side recovery.
- `server/app/ui.py:106`: build_fleet calls wearer_states(w) for every wearer returned by db.list_wearers(), so one wearer's stored +inf breaks the whole fleet page and fleet fragment for every operator.
- `server/app/ui.py:198`: _render_wearer (GET /ui/wearers/{wid}) also calls wearer_states; wearer_fragment does so at line 247.
- `server/app/ui.py:451`: POST /ui/wearers/{wid}/disable only needs an admin session plus CSRF and answers with a 303 redirect, so it remains usable with a CSRF token taken from a page that still renders (base.html:41 embeds it on every page with an operator; /ui/operators at 471 and /ui/audit at 556 do not call wearer_states).
- `server/app/wearers.py:200`: POST /api/v1/admin/wearers/{wearer_id}/disable — alternative recovery with the admin token or an admin session cookie.
- `server/.venv/Lib/site-packages/pydantic_core/core_schema.py:694`: FloatSchema `allow_inf_nan` — default True; pydantic/config.py:448-449 documents the same default for ConfigDict, and HeartbeatIn sets no model_config.
- `server/.venv/Lib/site-packages/starlette/requests.py:265`: `self._json = json.loads(body)` — stdlib decoder (installed starlette is 1.3.1 while server/requirements.txt:423 pins 1.6.0 for the image).
- `server/.venv/Lib/site-packages/starlette/middleware/errors.py:254`: ServerErrorMiddleware answers an unhandled exception with a 500 response (and re-raises for the server log), so the worker survives and the failure repeats on every page load.
- `android/app/src/main/java/org/cryomonitor/companion/ServerClient.kt:173`: `suspendedUntilT?.let { put("suspended_until", it / 1000.0) }` — the legitimate companion omits the key when not paused, so its next heartbeat (every 300 s, MonitorService.kt:1240) stores NULL and restores the dashboard unless the attacker re-sends.
- `server/app/main.py:525`: _pump_loop and its callees never read suspended_until, so dead-man evaluation, escalation delivery and ack handling are unaffected; the impact is confined to the operator dashboard pages.

poll_loop (server/app/telegram_poll.py:74-123) handles one getUpdates batch inside a single try block and persists the consumed offset (line 119-120) only after every update in the batch has been handled. ## Base compose trusts only 127.0.0.1 for X-Forwarded-For, which a bridge-networked container never sees from DSM's reverse proxy; unless the NAS .env overrides CM_FORWARDED_ALLOW_IPS, all internet callers share one login and one enrol rate-limit bucket and the audit records the proxy

`server/docker-compose.yml:FORWARDED_ALLOW_IPS-default:proxy-identity-collapse`

uvicorn installs ProxyHeadersMiddleware by default and reads the trusted-proxy list from the FORWARDED_ALLOW_IPS environment variable, defaulting to 127.0.0.1 (uvicorn 0.52.x config.py: os.environ.get("FORWARDED_ALLOW_IPS", "127.0.0.1")); the image CMD passes no --forwarded-allow-ips flag (server/Dockerfile:34) and the base compose sets FORWARDED_ALLOW_IPS to ${CM_FORWARDED_ALLOW_IPS:-127.0.0.1} (server/docker-compose.yml:56). For a peer not in that list the middleware leaves scope["client"] as the raw TCP peer (uvicorn proxy_headers.py: X-Forwarded-For is only read when client_host in trusted_hosts). The documented NAS topology (docs/DEPLOY-SYNOLOGY.md:82-85) has DSM's proxy connect to localhost:8081, the published host port of a compose service on the default bridge network; inside the container's own network namespace that connection arrives from a host address on the bridge (the owner's own record at openspec/changes/archive/2026-09-17-vps-deployment-kit/proposal.md:13-14 says the NAS logs showed 172.23.0.1 on every request), never from 127.0.0.1. So with the default, request.client.host is the same gateway address for every internet caller. Login keys its per-address throttle on a:{client} (server/app/operators.py:85-89; client comes from request.client.host at server/app/ui.py:144) and records a failure for any username (operators.py:98-100), so five failed POST /ui/login from anywhere, no valid username needed, make check_rate_limit raise 429 for every subsequent login attempt by any operator for 15 minutes; refused attempts are not recorded (the raise precedes record_login_attempt), so keeping the lock costs about one failed request per 15 minutes. Enrolment keys its in-memory 10-per-hour throttle on the same address (server/app/wearers.py:135-140,158-160) and counts every request before validating the code, so the eleventh and later POST /api/v1/enroll in any sliding hour, including legitimate ones, return 429. The login_failed/login/enrolled audit events store the collapsed client (operators.py:101-102,108; wearers.py:169), so attribution of an attack is lost. Scope of the availability effect: new dashboard logins and new phone enrolments only; operators with a live cm_session cookie (7-day TTL) keep working, and acknowledge paths (Telegram, ntfy, email ack tokens) and the phone API are unaffected. The repository's own tests show the mechanism (server/tests/test_proxy_headers.py:29-36) and the archived change left the NAS step 'set CM_FORWARDED_ALLOW_IPS to the bridge gateway' unchecked and marked optional (tasks.md:14-18), while openspec/specs/server-deployment/spec.md:8-16 requires per-client identity behind a proxy. Whether the production NAS .env overrides the default today is the decisive fact and is not readable in this audit.

**Claimed root cause:** The base compose ships a trusted-proxy default (127.0.0.1) that a bridge-networked container can never match for a host-side reverse proxy, the documented NAS deployment relies on an optional manual .env override to correct it, and the application's only brute-force defences and audit attribution key solely on request.client.host with no fallback that stays per-caller or fails safe when that identity collapses to one value.
